# ДЗ 2: пошук статей arXiv у Pinecone

Ідея роботи проста: шукати статті не лише за точними словами, а й за змістом запиту. Для цього назви й анотації перетворюються на вектори за допомогою SPECTER2 Base. Pinecone шукає серед цих векторів, а локально можна перевірити, чи змінюється видача при виборі іншої метрики. Окремо порівнюються два способи поділу довгих анотацій. [Умова завдання GoIT](https://www.edu.goit.global/uk/learn/43680627/49489220/52105942/homework).

## Як запустити

Команди нижче розраховані на Bash і Python 3.12. Дані беремо з [Kaggle](https://www.kaggle.com/datasets/Cornell-University/arxiv). Якщо завантаження попросить авторизацію, можна виконати `kaggle auth login` або використати `~/.kaggle/kaggle.json` ([довідка Kaggle CLI](https://github.com/Kaggle/kaggle-cli/blob/main/docs/README.md)).

```bash
cd 02
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
test -f .env || cp .env.example .env
kaggle datasets download Cornell-University/arxiv --unzip
```

У `02/.env` потрібно вписати свій `PINECONE_API_KEY`. Скрипти створюють три індекси в AWS `us-east-1`: `arxiv-papers`, `arxiv-chunks-fixed` та `arxiv-chunks-semantic`. У залежностях використано пакет `pinecone` замість старого `pinecone-client` з умови ([Pinecone Python SDK](https://sdk.pinecone.io/python/_modules/pinecone/client/indexes.html)).

```bash
(
  set -e -o pipefail
  mkdir -p logs
  for script in scripts/0[1-5]_*.py; do
    name="$(basename "$script" .py)"
    python -u "$script" 2>&1 | tee "logs/$name.txt"
  done
)
```

Це п’ять обов’язкових скриптів. Якщо на кроці `02` бракує пам’яті, його можна запустити окремо з `--batch-size 16`, а потім продовжити з `03`. Якщо JSONL лежить в іншій папці, для `01` є параметр `--input`. Тести запускаються командою `python -m unittest discover -s tests`. `.env`, `data/`, `embeddings/` і `logs/` не потрапляють у Git.

## Дані, модель та індекс

### Як зібрана вибірка

Для року публікації береться дата першої версії статті, а дата останнього оновлення використовується лише як запасна. Категорія теж одна: перша з поля `categories`. У початкових рядках снапшота багато старих робіт, тому до 1 000 місць із 10 000 відведено під додаткові статті `cs.LG`, щоб було по чому перевірити фільтр за останні п’ять календарних років. Це вибірка для демонстрації пошуку, а не зріз, який рівномірно представляє весь arXiv. Щоб відтворити річний фільтр, можна передати `01_prepare_data.py --as-of-year 2026`.

### Чим відрізняються Pinecone, Qdrant і Chroma

Для цієї роботи Pinecone зручний тим, що не доводиться піднімати й обслуговувати сервер. Це пропрієтарний керований сервіс ([огляд Redis](https://redis.io/blog/vector-database-alternatives-rag-pipelines/)). Якби індекс мав працювати на власній інфраструктурі й потрібно було налаштовувати фільтри або використання пам’яті, я б спробував [Qdrant](https://qdrant.tech/documentation/overview/): його [рушій під Apache 2.0](https://github.com/qdrant/qdrant) можна розгорнути самостійно. Для прототипу в ноутбуці почав би з [Chroma](https://github.com/chroma-core/chroma): вона теж під Apache 2.0 і може працювати локально, без мережевого запиту. Називати одну з них найшвидшою без тесту не має сенсу. Для чесного порівняння я б дав усім той самий корпус і фільтри, а тоді порівняв затримку, пропускну здатність і recall@5.

### Чому SPECTER2, а не MiniLM

У [картці SPECTER2 Base](https://huggingface.co/allenai/specter2_base) сказано: “SPECTER2 has been trained on over 6M triplets of scientific paper citations”. Там же перелічені задачі, для яких модель донавчали з адаптерами: `Classification`, `Regression`, `Proximity (Retrieval)` і `Adhoc Search`. Для пошуку за назвами й анотаціями наукових статей це доречна відправна точка. [all-MiniLM-L6-v2](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2) універсальніша й дає компактніші вектори: 384 замість 768. Це не означає, що SPECTER2 точно виграє в пошуку: прямого порівняння моделей тут не було.

У коді використовується саме `specter2_base`, без адаптерів. Для статті модель отримує `title [SEP] abstract`, після чого береться вектор першого токена (CLS), як у [прикладі з картки моделі](https://huggingface.co/allenai/specter2_base). Автори окремо радять адаптер для коротких запитів; тут для статей, чанків і запитів використовується той самий базовий енкодер.

### Чому cosine

[Картка моделі](https://huggingface.co/allenai/specter2_base) не встановлює однієї метрики для всіх задач. Для цього індексу вибрано `cosine`, бо він порівнює напрями векторів. Cosine дорівнює скалярному добутку, поділеному на добуток норм. Після L2-нормалізації обидві норми дорівнюють одиниці, тому cosine і dot product дають той самий порядок при точному пошуку. Метрика важлива ще й тому, що від неї залежать числові оцінки, які повертає індекс.

У Pinecone зберігаються 768-вимірні вектори та короткі метадані. Анотація в метаданих обрізається до 500 символів, автори до 200, а повну анотацію можна знайти в Parquet за `arxiv_id`. Це дозволяє не відправляти зайвий текст і залишатися в межах [лімітів Pinecone на запис і пакет](https://docs.pinecone.io/guides/index-data/upsert-data). Повторний запуск на тому самому Parquet перезаписує ті самі ID у тому самому namespace; інша вибірка отримує окремий namespace.

## Що показав пошук

На локальному тесті з 30 статтями всі три метрики повернули ті самі п’ять ID в тому самому порядку. Dot product і cosine мали невелику різницю в останніх знаках через округлення. L2 дав інші числові значення, але відстань сортується від меншої до більшої, тому порядок залишився тим самим.

Без нормалізації результат міг би відрізнятися. Наприклад, для запиту `(1, 0)` вектори `(1, 0)` і `(10, 0)` мають однаковий cosine. Dot product поставить `(10, 0)` вище, а L2 поставить вище `(1, 0)`, бо він ближчий до запиту.

Для фільтрів A і B використовується одна фраза, `reinforcement learning`. A допускає лише `cs.LG` за вибране п’ятиріччя, а B бере будь-які категорії до 2015 року. У перевіреній вибірці під ці умови підпадають 1 000 і 9 000 статей відповідно. Це кількість кандидатів, а не доказ того, що в обох групах знайдуться хороші результати. Щоб їх порівняти, треба переглянути назви й уривки з обох топ-5 після запуску в Pinecone.

## Що змінилося після поділу анотацій

Fixed-size бере по 100 слів із перекриттям у 20. Такий поділ простий, але межа може потрапити всередину речення: наприклад, висновок залишиться в одному чанку, а його умова в іншому. Поділ за реченнями збирає цілі речення до ліміту, тому такі уривки зазвичай зручніше читати окремо. Якщо одне речення саме не вміщується, його все одно доводиться ділити. В обох випадках скрипт перевіряє бюджет 512 токенів разом із заголовком і спеціальними токенами.

Серед 30 найдовших анотацій основної вибірки 13 мали понад 512 токенів. Fixed-size дав 97 чанків із середньою довжиною 88,3 слова, поділ за реченнями дав 99 чанків із середньою довжиною 73,0 слова. У другому варіанті довелося примусово поділити два речення. Ці числа показують різницю між способами нарізання, але не кажуть, який дає кращу видачу.

Перекриття потрібне, щоб слова біля межі хоча б один раз потрапили в чанк разом із сусідами. Якщо перекриття збільшити, чанків стає більше, а в топ-5 можуть повторюватися майже однакові уривки однієї статті. Тому вивід `05` показує не лише оцінки збігів, а й кількість різних статей серед результатів.

## Додатково: BM25 і RRF

`06_hybrid_search.py` не потрібен для обов’язкової частини. Він будує BM25 за назвою, анотацією та іменами авторів і зводить цей список із результатами Pinecone. RRF додає за кожну позицію `r` оцінку `1 / (k + r)`, не порівнюючи сирі оцінки BM25 і cosine. Документ може не ввійти в топ-5 жодного методу, але потрапити в спільний топ-5, якщо він добре стоїть в обох списках кандидатів. При `k=1` перші позиції важать відносно більше, ніж при `k=60`.

Для `BERT fine-tuning` і запиту з `Yann LeCun` є сенс перевірити точні збіги, а для перефразованого запиту про розпізнавання емоцій я б спочатку подивився на векторний пошук. Це припущення: живої видачі для цих трьох запитів тут немає. Якщо включати додаткову частину до здачі, `python scripts/06_hybrid_search.py` надрукує таблицю для README, результати для `k=1` та ID, які з’явилися лише в гібридному топ-5.

## Висновки

### Коли шукати за змістом, а коли за словами

Якщо запит описує ідею іншими словами, я б почав із семантичного пошуку. Якщо відома назва методу, абревіатура чи автор, спочатку перевірив би BM25. У локальному зразку запит про розпізнавання об’єктів повернув статті про фрактали й графи. Це хороший приклад того, чому високий cosine не варто сприймати як гарантію: найближчий документ не обов’язково доречний. Пошук за чанками дає змогу прочитати конкретний уривок і швидше перевірити, чи збіг справді по темі.

### Який розмір чанка обрати

У 10–15 словах легко втратити, до чого саме належить висновок. А в чанку на 500+ слів потрібна деталь може загубитися серед інших тем або опинитися за межами 512 токенів [SPECTER2](https://huggingface.co/allenai/specter2_base). Для пошуку короткого факту я б почав із кількох цілих речень, а для опису методу залишив би більше контексту. Підбирати розмір краще на реальних запитах, а не лише за кількістю слів.

### Чи змінилася б видача з `euclidean`

Для одиничних векторів:

```text
||u − v||² = (u − v) · (u − v)
           = ||u||² + ||v||² − 2(u · v)
           = 2 − 2 cos(u, v)
```

Чим більший cosine, тим менша L2-відстань. Тому точний пошук з `euclidean` дасть той самий порядок, але не ті самі оцінки. Поріг, підібраний для cosine, не можна просто скопіювати в L2. У реальному індексі при дуже близьких оцінках можливі відмінності через округлення або наближений пошук.

### Що робити з 10 мільйонами статей

За [документацією Pinecone](https://docs.pinecone.io/reference/api/database-limits/object-limits), Starter підтримує до п’яти serverless-індексів у регіоні AWS `us-east-1` і 2 ГБ сховища на організацію. Для цього ДЗ потрібні три слоти. Для 10 млн статей самі вектори `float32` розмірності 768 займуть приблизно 30,7 ГБ ще до метаданих та індексних структур. Тут я б уже рахував ембеддинги порціями на GPU, зберігав проміжні файли, щоб можна було продовжити після збою, і порівнював платний сервіс із самостійним розгортанням за ціною, затримкою та якістю пошуку.

```text
Articles: 10,000; invalid records encountered: 0
Extra recent cs.LG articles: 1,000; eligible for filter A: 1,000; eligible for filter B: 9,000
```

```text
02_embed.py --device cpu --batch-size 8
Encoder: allenai/specter2_base:cls:l2:512:v1
```

Обидві стратегії нарізання перевірено локально на основній вибірці. Хмарні кроки перевірено з імітацією Pinecone, тому фактичного виводу з облікового запису Pinecone тут ще немає. Перед здачею потрібно додати до README вивід `01`–`05` із повного запуску й коротко описати, що саме повернули фільтри A і B та який уривок виявився кориснішим у порівнянні двох способів нарізання.
